## What the code shows (facts, with lines)
- `app/librarian.py` sets `code_root = Path(__file__).parent.parent` and loads the v7 door by file name.
- **The v7 door:**
  - validates `review-loop-v7.json` (schema `review-loop-pins/5`, an exact key set, 17 tool names);
  - hash-pins v4–v6 and pass01/pass02;
  - resolves every RESOLVE tool;
  - then runs the workbook in a **subprocess** with `cwd=code_root`.
- **Hard-coded roots** (the packaging seam):
  - pass03 `REPO` (line 21), which loads pass02 **at import** from `REPO`;
  - pass02 `REPO` (line 20), which loads pass01 at import;
  - pass01 `REPO` (line 22), used by `pin_file`, `call_json cwd`, `writable`, `form_view`;
  - `review_loop`, `construct`, `prime_cycle` and `return_access` each have `ROOT = D:\Git\lib-build`.
- **Consequence:** a copied app root runs its own door and workbook bytes, but the workbook resolves code-root data and predecessor imports from the LIVE checkout. That is exactly the "A-app" wrong-root effect of 05.16 and 05.17.
- **pass02 `writable`:** the only checkout book that record and publish may write is `wb.REPO/00.kernel/00.00.10.work`. Any other book inside `wb.REPO` is refused.
- **The cycle path:** `attempt_cycle` calls `review_loop prepare --fixture-root BOOK`, and `review_loop` refuses a fixture root inside its hard-coded ROOT.
  - So in production (book inside lib-build) the cycle cannot commit.
  - On a copy OUTSIDE lib-build it may proceed.
  - **This is a fixture-versus-production divergence to measure, not to repair here.**
