# Desk operations - ideas extracted from a prototype
date: 2026-10-31
who: Codex Prime
state: N4NN development material; proposed, not approved architecture or build instructions

## Why this page exists
The Director commissioned the grok.com build to see what a model could produce.
Useful material can land in N4NN for discussion before the next 05 is drafted.
It is not automatically the app, a competing architecture to maintain, or a
validated reusable build recipe. This page extracts useful ideas, not wholesale code.

## Idea 1 - a small vocabulary of work operations
The prototype organizes work into record-task, register, show, submit-return,
retrieve, review, recover and pending. Their value is a visible usable sequence
over work-book records: each has explicit input, an output, and a handback.
Candidate principle: give a model a small set of supported requests whose compute
implementation handles structural work. Command names and exact schemas remain
open; no reason to adopt all prototype names or duplicate existing tools.
In particular, split a worker's assertion of completion from verified custody,
and split custody from intelligent review and Director approval.

## Idea 2 - construct records and readable faces together
A structured task can construct its page/face, expected outputs and references;
a supplied judgment can construct its full readable review in the same work line.
This is useful because addresses/layout cease to be improvised by each model.
The full review belongs on N5NN/05.NN. N7NN keeps its local tailed review. Supporting
JSON/evidence must remain linked. Do not make a duplicate JSON task silently become
another authority: we still need an explicit rule for which record owns which fact,
how the face relates to it, and how disagreement is reported and reconciled.
The prototype's claim that faces are projections is a proposal to examine, not
permission to demote existing work-book instructions or the assignment selector.

## Idea 3 - questions and handback survive the operation
The prototype carries unresolved questions with the return and review, and exposes
them again on recovery. Useful principle: a reply, minority finding or unanswered
question stays attached to the relevant work until an attributed disposition.
Do not reduce this to a cosmetic pending flag or erase it when a later check passes.
Where a next actor/action exists, record whether intelligence supplied it or compute
derived it from a declared route. Compute must not invent authority or semantic
resolution from a status label. Contradictory identity or stale evidence takes
precedence over an apparently actionable next step.

## Idea 4 - explicit operation results and inspectable failures
A structured result with operation, state, evidence links and limitations can help
models use tools without reparsing prose. But a generic refusal code is insufficient
by itself. Link the applicable contract/version, the observed failed check, preserved
request/partial evidence and the correction/help/escalation route. See 0416/01.003.
Mechanical refusal, unavailable capability, incomplete input, semantic disagreement
and missing authority are distinct. Intelligence can interpret or escalate; compute
must not manufacture a rejection rule where the kernel/contract is silent.

## What to leave experimental
The prototype's parallel task/receipt/review schemas, zero-only addresses, permanent
synthetic labels and Unix-specific I/O are not adopted. Its standalone loop offers
examples for reasoning about the app, not a mandate to replace current modules.
N5NN -> N1NN and N7NN page-local routing remain the Director's existing rule.

## Questions before a future 05
- Which existing record owns each fact, and which readable face is constructed?
- What is the smallest operation vocabulary Prime actually needs for one return?
- How does Clerk return help or escalate without disguising judgment as a format rule?
- What is the actual state when custody is intact but task/release/review is stale?
