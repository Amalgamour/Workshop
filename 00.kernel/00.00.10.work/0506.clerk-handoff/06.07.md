## Projection

The command is `clerk.py show --store S --job ID --json [--instructions-base BASE]`. It calls the same `existing_store`, `_find_view`, and `classify` path as human `show`. It does not parse event files a second time.

The reducer keeps four fields that human text does not print, and only after the checks it already makes:

- `claim_by` is the validated claim's `by`, set when that claim is accepted.
- `delivery`, `evidence`, and `return_by` are set only when the returned event and the completion witness agree and the returned object passes the existing checks.

Stdout is one canonical JSON object, the same `canonical()` rules as the store, including the trailing LF. There is no `result ok`, `result findings`, or `result refused` line. Stderr is empty. Argparse syntax errors stay on stderr with exit 2, and that stdout is not this document. Inspection never creates, truncates, or deletes a store file.

Top-level keys, exactly: `schema`, `job_id`, `state`, `job`, `claim`, `returned`, `checks`, `problems`.

`job_id` is the requested id even when `job` is null.

`state` is `queued`, `claimed`, or `returned` only when the view is not structural and its status is that phase. `incomplete` is a view whose status is already `incomplete`. Every other structural view is `corrupt`. `unknown` is no matching job, a refusal (missing store, bad id, git tree, path shape), or an `OSError` that escapes `show`. A refusal to inspect is `unknown`, not `corrupt`: the record was not classified.

`job`, `claim`, and `returned` are null unless the phase is clean. Queued exposes `job` only. Claimed exposes `job` and `claim`. Returned exposes all three. An incomplete or corrupt view can hold a validated prefix in memory; the document does not. Null `returned` on a clean queued or claimed job is normal. The projection does not invent outputs.

`job` is the validated seven-key queued object. `job_id` stays on that object because it is part of the queued record. Assignee, reviewer, instructions, expected outputs, release, and routed_by stay owned there.

`claim` is `{"by", "token"}`. `by` is `claim_by` from the validated claim. The reducer already requires that actor to equal the job assignee before it accepts the claim. `token` is the claim token already on the view. Both are labels, not authentication.

`returned` is `{"by", "delivery", "evidence", "artifacts"}` from the validated return. `artifacts` is the list recorded on that event. It is not a new hash of the current outbox. A changed artifact stays inside `returned` and is reported by the artifact check.

`checks` values are strings:

- `events`: `ok` when `chain_ok` and the view is not structural; `unreadable` when the diagnosis is `unreadable job`, `job directory is unreadable`, `returned event is unreadable`, or starts with `invalid event`; `broken` for any other structural view; `not-applicable` when there is no view.
- `completion`: `ok` only for a clean returned view, including when a later artifact byte change is reported; `not-applicable` for a clean queued or claimed view and when there is no view. Diagnosis map: `partial completion witness` → `partial`; `completion witness without returned event` → `missing-event`; `returned event without completion witness` → `missing-witness`; `completion witness mismatch` and `invalid completion witness` → `mismatch`; a diagnosis that starts with `planted completion metadata` → `mismatch`. Any other structural diagnosis is `not-applicable`. `not-applicable` is not a passed check.
- `artifacts`: `not-applicable` unless `state` is `returned`. For a clean return, `inspect_artifacts` runs once. `changed` when one of its lines contains `artifact changed`; otherwise `ok`.
- `instructions`: `not-applicable` when no usable job is presented; `not-checked` when a clean job is present and no base was supplied; `usable` or `unusable` from `instruction_status` when a base is supplied. `job.instructions` remains the recorded hash. `unusable` means the file at that base does not match. It does not make the record structural-bad. `not-checked` can still exit 0.

`problems` is a list of objects. Every object has `kind` and `detail`. `artifact-changed` also has `path`. Kinds: `unknown`, `incomplete`, `corrupt`, `artifact-changed`, `instructions-unusable`, `filesystem`. The list is empty only on exit 0. On a clean phase the order is artifact problems in `inspect_artifacts` order, then one `instructions-unusable` problem when the base check fails. Structural detail is `view.diagnosis` exactly, without the human `bad state:` wrapper. Refusal detail drops one leading `refused: `. An `Incomplete` raised out of `show` is state `incomplete`, kind `incomplete`, with one leading `incomplete: ` removed. The current reader does not raise `Incomplete`; classify records those conditions on the view. Filesystem detail is `ClassName: strerror` (or `ClassName:` plus `str(exc)` when strerror is empty). An `OSError` that classify already turns into `job directory is unreadable` stays a corrupt projection. It is not the filesystem JSON path. A git-tree or path refusal is state `unknown`, kind `unknown`.

Exit codes: 0 when state is `queued`, `claimed`, or `returned` and `problems` is empty. 1 when state is one of those three and every problem is `artifact-changed` or `instructions-unusable`. 2 for unknown, incomplete, corrupt, refusal, and filesystem. Exit 0 does not occur with a nonempty problem list, and it does not occur for `unknown`, `incomplete`, or `corrupt`. A returned job with a changed artifact is a valid recorded object and exits 1. The document is not an approval, a closure, or an acceptance record.
