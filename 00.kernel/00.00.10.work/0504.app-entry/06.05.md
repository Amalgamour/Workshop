## What this pack narrows
DESIGN.md section 4 shows one shared `bridge/input` and one shared `bridge/output`. This pack requires a fresh exclusive input directory and a fresh exclusive output directory for each new delivery. The glue therefore keeps declared bytes at `bridge/declared/<job path>` and launches only from `bridge/delivery/<delivery_id>/input` into `bridge/delivery/<delivery_id>/output`. A pre-existing per-delivery directory, store directory, provenance file, or temporary name is refused. It is not adopted and not deleted.

## Exchange
`bridge-test` uses `validate_context(..., execute=True, runner_root=code_root)`. The fixture record must be `released`, and a new delivery's `work_ref` must equal that record's `current_work`. The job file is exact-key `librarian-bridge-job` version 1. It has no root, argv, store, release, or container. The configured kind list allows only `protocol test worker`. The envelope release is `{by: "fixture record", ref: "<record path> sha256 <hash>"}`. That text is recorded evidence. It is not an authentication of a person or a model.

Pins for the eight lab files are checked, by reading bytes, before any `worker_bridge_pinned` import. The package name is private. `sys.path` is not changed. A mismatch refuses with `stop:` and does not import. The same-user window between the hash read and the import is not closed. The pin check is development integrity, not an operating-system boundary.

Replay of the same job bytes passes the stored request object to the adapter. The envelope is not rebuilt, so a later assignment hash or timestamp cannot change `request_sha256`. A different job under the same delivery id refuses. The refusal says this call did not launch. If a launch record is already there, the refusal says that record remains. It does not say that no launch ever happened.

`bridge-status` uses `execute=False`. It stays available when the fixture record is later `returned` or `accepted`, and when `current_work` changes. It correlates provenance, the stored request, and the receipt, and it checks that those paths resolve inside the designated container. The current record alone is not enough.

`bridge-recover` also uses `execute=False`. The recovery file is exact-key `librarian-bridge-recovery` version 1 and names the delivery, the original request hash, a reason, and a requester. That is scoped invocation evidence, not a model or human authentication system. Recover writes a receipt only from a fully recorded attempt. It never launches.

Provenance is one file, `bridge/provenance/<delivery_id>.json`. It associates the stored request with the fixture, the work ref, and the declared job hash. It is not a second job ledger. The adapter keeps its own request, launch, attempt, and receipt store.

## Exit mapping
0: transport `delivered`, collection `collected`, claimed outcome `done`, not uncertain.
2: refused on this call. Stderr starts with `stop:`. Stdout is empty. A conflicting id is exit 2 and is not described as a clean pre-launch refusal of an untouched delivery.
3: transport `delivered` with collection `uncollected`, or a collected claim of `failed`.
4: uncertain or not collected. This includes unknown, accepted-not-launched, launch-failed, crashed, timeout, output-limit, incomplete-output, and malformed. Unknown is printed as `collection: not collected`. A new delivery id after uncertainty is a separate decision. Nothing relaunches automatically.

Collection is not approval. Every report says `review: not performed` and `acceptance: not performed`.

## Trust boundary
Same-user Python is not sandboxed. Path and link checks are not a promise against a later change. The adapter kills only the direct child. A descendant that still holds a pipe is named in `cleanup.retained` and is not tree-killed. There is no exactly-once promise. `launch.json` is the adapter's one-launcher guard for one delivery. Normal `run` stays refused. No model profile is configured. Nothing is seated or activated.

This process cannot create a file symlink (`WinError 1314`). Directory junctions come from `mklink /J`. Hard links come from `os.link`. A junction is removed with `rmdir` before a parent tree is deleted.
