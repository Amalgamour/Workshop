## #03 — Receipt, replay, status and recovery
Example operation: fixture-ok counts the three nonblank input lines and writes
the expected count artifact, then the adapter verifies the ids/hash and stores
its receipt. Print transport, claimed outcome, collection, receipt path/hash,
review: not performed, acceptance: not performed. Collection never means approval.
For identical bridge-test replay, reuse/verify the ORIGINAL recorded request identity;
do not rebuild it with a new timestamp or changed assignment-record hash. A changed
job under the same delivery ID refuses; no automatic relaunch after uncertainty.
Do not recreate existing per-delivery I/O directories on replay/status/recovery.
Status is read-only and must work after returned/accepted state or current-work
changes. Correlate stored provenance/request/receipt and validate their paths inside
the designated container before relying on them; current record alone is insufficient.
Recovery writes evidence but never launches. Require an explicit exact-key local
recovery request naming delivery, original request hash and reason/requester; this
is scoped invocation evidence, not a model/human authentication system. Do not
require a fresh worker-launch release merely to inspect history or recover evidence.
Preserve incomplete-output, retained pipe details, timeout, malformed output and
crash uncertainty. Cover unknown/accepted-not-launched/launch-failed/output-limit
states honestly. Document exit mapping; unknown is never collected. Same-user
Python remains unsandboxed; no process-tree termination or exactly-once promise.
