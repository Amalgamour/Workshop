## Use

This is the main reference for every prime on this book. Read it at boot, after `AGENTS.md` and `00.md`.
Before you write a pack, name the lane below it serves and the finish-line step it moves. If it serves no lane, do not write it.
The queue page `0415.queue` tracks packs. Its Goal line points here. This page sets the goal; the queue does not.
This page changes only by the Director's word. A prime proposes a change as a dev line; it does not edit this page to fit its work.

## Long goal

Each page is a slice. A slice is worked in passes. Some pages are right in one pass; some take dozens. Each pass leaves what it learned on the page.
When every page is right, a last pack carries all the learning. A fresh builder, given only that pack and the pages, rebuilds the whole project.
So write every pass for that fresh builder: the page must say what it is, why, and how it was tested, with nothing kept in chat or memory.

## Finish line 1: the kernel core runs

Done means all of these are true at once, on branch `rebuild`:
1. The loader is seated at `0302.run` (the Director seats it).
2. `jobs`, `check`, `clerk` and `slot` each run through the seated loader from their compute pages `0303` to `0306`.
3. Cards follow the card rule (Decisions, 3).
4. A cold start finds this book from the repository door without a remembered path (`1001.assessment` F02).
5. The acceptance test passes.

The acceptance test, from `1001.assessment` F05. In an isolated checkout, using only the supplied entry and the seated loader:
- find the current work
- make a stamped page with compute
- save a decision or a note
- open a batch, return on it, and close it
- resume from a second process and find where it stopped
- refuse an unreleased job and a changed source

It records every manual step, path typed by hand, or unmet dependency. One manual workaround is a fail.
Write the test first. It fails today. Each lane moves it toward passing.

## Lanes

One lane is one number. A builder owns only its lane's folders, `01NN` to `05NN` for its number. A builder never edits another lane's folders.
Each lane works on its own branch, `rebuild-<title>`, and asks to merge into `rebuild` with a pull request.

```text
lane 0  review     the prime and the review layers   backlog: returns 0101 to 0106, draft 0519/05.01
lane 1  slot       06    re-hash the slot source (0106.slot #02 >stop); port to 0306.slot; return on 0106.slot
lane 2  run        02    card rule B on the loader and on 0303.jobs/02.md; the seat packet for 0302.run
lane 3  acceptance 20    write the acceptance test above, failing; run it after each merge
lane 4  review     21    design the compute review check (layer 1 below) in 0421.review, then build it
lane 5  boot       22    one boot route: 00.start.md, 00.readme.md, 0011.contents (F02, F03). waits on a Director decision
later              the pack-lint false pass (F01, in 0305.clerk); one stamp function for clerk, face and jobs; a size limit for tools
```

Order:
- Lanes 1, 2 and 3 run now, side by side. Their folders do not overlap.
- Lane 0 runs now.
- Lane 4 starts with its dev design. Lane 5 starts when the Director decides the boot profile.
- The `0302.run` seat waits on lane 2. Finish line 1 waits on all of them.
- Later work waits on finish line 1. It touches the tools every lane uses.

## Decisions

From the Director, chat 2026-10-26.

1. **Review is layered.** One model's blind spot must not become the project's.
   - Layer 1, compute. A check reads each return. It confirms that the return touched only its lane's folders, that the tests pass, that the hashes match, that every task `#NN` has a line, and that nothing in the shared doors changed. A failure goes back to the builder. No model judges it.
   - Layer 2, the Grok review bot. It closes the returns that passed layer 1 and have no open `>note` or `>stop`.
   - Layer 3, a model of another family than the builder (today, Claude). It answers every `>stop`, every design question, and any change to a shared door. What needs a decision goes to the Director in dev.
   - When layer 3 finds an issue that a check could catch, that check is added to layer 1. Then the Grok bot can pack a new pass on that page itself.
2. **Merging.**
   - A lane merges into `rebuild` after layers 1 to 3 pass. The reviewer that closes the review merges the pull request.
   - `rebuild` is where work stops and is checked before it goes to the Director.
   - Only the Director merges into `main`. He is the responsible party.
3. **The card rule (B).** Compute is dumb and strict.
   - A card `02.md` holds only `runs:`, `uses:` and `args:`.
   - What a module is, its lifecycle, and its test go on face `01`.
   - The loader refuses any other card line.
   - A new card key is a dev decision, never a quiet edit.

## Never

- Approve, promote, seat or lock. Those are the Director's. A model writes the request; he acts.
- Pack around a waiting return. Review first.
- Grow a shared tool to suit one lane.
