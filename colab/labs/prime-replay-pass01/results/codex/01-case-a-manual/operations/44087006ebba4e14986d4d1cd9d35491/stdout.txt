1: # CONTRACT — prime-bench-pass01
2: 
3: Subject: the bounded Prime benchmark harness for 0513.bench-build/05.01.002. Design: 0414.bench/01.md.
4: Module: labs/prime-bench-pass01/prime_bench.py. Standard library only. Builder contract for a lab; it seats no law.
5: 
6: ## What it is, and is not
7: It prepares fixed cases into fresh run folders, records what a coordinator collected, checks deterministic evidence, binds a supplied reviewer record, and tabulates runs.
8: It does not call a model, launch or drive a session, hold credentials, use the network or Git, write a live page, run an app fixture, or decide semantic quality.
9: It does not reserve, capture or inspect a return. The N1NN tools do that; `export` prints the capture command and does not run it.
10: Fixture tests use labelled SYNTHETIC responses and demonstrate the instrument only, never model performance.
11: 
12: ## Bench version
13: `bench.json` (`prime-bench/1`) lists, each with sha256 and bytes:
14: - every case file under `cases/<case_id>/candidate/`, `evaluator/` and `coordinator/`;
15: - `conditions.json`;
16: - the support files the assisted condition copies, by repository path.
17: 
18: The bench version is the sha256 of the exact bench.json bytes. `validate` re-hashes every listed file, checks that no unlisted file is present in a case folder, and checks the support pins against the live repository. Any drift is exit 1. A case's revision changes only with a new bench.json.
19: 
20: ## Case files
21: - `candidate/TASK.md` and `candidate/sources/*`: the only case material a tested session sees. No case id, family, variant, key or canary.
22: - `evaluator/key.json` (`prime-bench-key/1`): `case_id`, `revision`, `canary`, `outcomes` (acceptable outcome labels), `must_mention` (groups of alternatives; each group needs one case-insensitive hit), `must_quote` (exact strings), `must_not` (regular expressions).
23: - `evaluator/rubric.json` (`prime-bench-rubric/1`): `case_id`, `revision`, `scale` (allowed integer scores), `items` (`id`, `text`).
24: - `coordinator/meta.json` (`prime-bench-case-meta/1`): `case_id`, `revision`, `family`, `variant`, `matched_with`, `label` SYNTHETIC, `decisive_evidence`, `ambiguity`, `provenance` (repository path, sha256 and the rule each case relies on).
25: 
26: Families: `correction`, `false-completion`, `design-fork`, `complete`. Each has variants `a` and `b`, matched to each other.
27: 
28: ## Conditions
29: `conditions.json` (`prime-bench-conditions/1`). `baseline`: ordinary read, search and command tools inside the candidate folder. `assisted`: the same, plus the copied reviewed prime_review.py (805995a1…) with its README and CONTRACT under `support/`. Task text and sources are byte-identical across conditions. The generated PROMPT.md differs only in its Tools paragraph.
30: 
31: ## Commands
32: Every path argument is absolute, local, not UNC, and has no link, junction or reparse point in itself or any ancestor. JSON input is strict (no duplicate keys, no non-finite numbers, exact keys, size limits).
33: 
34: ```text
35: python -B prime_bench.py validate [--json]
36: python -B prime_bench.py prepare --investigation ABS --run-id ID --case ID --condition baseline|assisted --model-label TEXT --effort-label TEXT
37:                                  --fresh-session S --workspace-confined S --tool-log S --usage S --run-dir ABS --candidate-dir ABS [--json]
38: python -B prime_bench.py collect --run-dir ABS --expect-run ID --expect-condition C --status completed|failed|abandoned [--reason TEXT]
39:                                  --label SYNTHETIC|ACTUAL --session-label TEXT --isolation-used fresh|shared|unknown
40:                                  [--response ABS] [--tool-log ABS] [--tool-events ABS] [--usage ABS] [--started ISO] [--finished ISO] [--intervention TEXT] [--json]
41: python -B prime_bench.py event   --run-dir ABS --kind correction|intervention|note --text TEXT [--attachment ABS] [--json]
42: python -B prime_bench.py assess  --run-dir ABS [--json]
43: python -B prime_bench.py review  --run-dir ABS --record ABS [--json]
44: python -B prime_bench.py compare --run-dir ABS [--run-dir ABS ...] [--json]
45: python -B prime_bench.py export  --run-dir ABS [...] --investigation ABS --dest ABS
46: ```
47: S is `supported`, `unsupported` or `unknown`.
48: 
49: Exits: 0 done or a shaped result; 1 bench drift, a deterministic mismatch reported by validate, or a partial write; 2 refused input. No traceback on bad input.
50: 
51: ## Investigation record
52: `prime-bench-investigation/1`: `page` (07NN.slug in 0701–0799), `pass` (05.NN), `question`, `director_replies` (each `reply` kept byte-exact, `source_path`, `source_sha256`), `sources` (path and sha256), `coordinator_label`. `prepare` binds its sha256 into run.json. `compare` and `export` refuse runs bound to different investigations, and `export` refuses an investigation file whose sha256 differs from the runs'.
53: 
54: ## prepare
55: - Run id `^r[0-9]{4}$`. Labels are 1–80 printable characters.
56: - Run and candidate folders must both be absent, under an existing real parent, outside the repository, and neither inside the other.
57: - `validate` runs first; drift refuses.
58: - The candidate folder gets `PROMPT.md`, `TASK.md`, `sources/` and, for assisted only, `support/`. Copied support files are re-hashed against their pins.
59: - Leakage gate: no canary of any case and no evaluator or coordinator file's bytes may appear in any candidate file. A hit refuses and is reported.
60: - The run folder gets `COORDINATOR.md` and, written last, `run.json` (`prime-bench-run/1`): run id, bench version, investigation sha256, case id and revision, condition, labels, declared capabilities, candidate folder, key, rubric, task and candidate file pins, and a `prepared_at` UTC clock reading.
61: - Files are created exclusively. A failure leaves what was written, reports `partial` (exit 1) and lists it. A run folder without run.json is never collected. A retry into an existing folder refuses. Nothing is deleted or resumed.
62: 
63: ## collect
64: - The run folder must hold a valid run.json whose run id and condition equal `--expect-run` and `--expect-condition`; otherwise `wrong-identity`, exit 2.
65: - A `completed` run needs `--response`. `failed` and `abandoned` need `--reason` and may carry a partial response.
66: - Response: exact bytes copied, at most 1 MiB. If its first non-blank line is `Run: <id>` for another run, `wrong-identity` refuses. A missing run line is recorded as `identity: missing`.
67: - Optional raw tool log (exact bytes, 8 MiB), normalized tool events (`prime-bench-tool-event/1` JSONL: `tool`, `at` or null), usage JSON (non-negative integer fields only, `source` text). Missing means `unavailable`.
68: - `--started` and `--finished` are ISO-8601 with offset, recorded as coordinator-supplied.
69: - Any canary in the response or raw tool log sets `leakage: true`.
70: - Written as `collected/` plus `collection.json` (`prime-bench-collection/1`), last. A second collect refuses read-only: `already-collected` when every supplied byte and field is identical, otherwise `conflict`.
71: 
72: ## event
73: Appends `events/NNNN.json` (`prime-bench-event/1`) with kind, text, an optional exact attachment, and the sha256 of collection.json it follows. The original collection is never changed. An `intervention` event makes the run unclean.
74: 
75: ## assess (read-only)
76: Refuses (`key-changed`, exit 2) if the live key, rubric or task differs from the pins in run.json. Otherwise prints `prime-bench-assessment/1`:
77: - `run_line`: matched or missing;
78: - `outcome`: the first `Outcome: <label>` line, and whether it is in the key's `outcomes`;
79: - `must_mention`, `must_quote`, `must_not`: per entry pass or fail;
80: - `canary_absent`;
81: - `deterministic_pass`: all of the above pass.
82: 
83: These are string checks. They are not a judgment that the review is right.
84: 
85: ## review
86: Supplied `prime-bench-review/1`: `run_id`, `case_id`, `case_revision`, `rubric_sha256`, `reviewer_label`, `blind_to_condition` (true, false or null), `scores` (exactly one per rubric item, each in the scale), `reviewer_minutes`, `director_attention_events` (null or non-negative), `notes`. Identity, case revision and rubric sha256 must equal run.json, else `wrong-identity` or `rubric-changed`, exit 2. Stored as exact bytes in `review.json`; a second record is `already-reviewed` when identical, otherwise `conflict`.
87: 
88: ## compare and what is counted
89: Refuses mixed bench versions, mixed investigations, a run folder given twice, two folders with one run id, and any key change.
90: For each run: status, label, condition, labels, clean or the reasons it is not, deterministic results, reviewer scores when supplied, elapsed seconds when both times were supplied, tool-event count when events were supplied, usage fields as supplied, correction and intervention event counts.
91: 
92: A run is **clean** only when: status completed; fresh-session and workspace-confined declared `supported`; isolation used `fresh`; its session label is used by no other run in the comparison; no intervention in collection or events; no leakage; identity matched. Unclean, failed, abandoned and uncollected runs are listed with reasons and counted; they are never dropped.
93: 
94: Counted, exactly:
95: - runs per condition by status and by clean;
96: - clean runs whose deterministic checks all pass;
97: - per rubric item, the number of clean reviewed runs and the sum of their supplied scores;
98: - elapsed, tool events and usage per run, or `unavailable`.
99: 
100: Not computed: ratios between conditions, time or token savings, rankings, a pass score. A SYNTHETIC label is printed on the report whenever any run is SYNTHETIC.
